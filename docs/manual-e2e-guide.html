What has not been completed

These categories distinguish missing product work from code awaiting configuration or validation.

Missing or partial implementation

  • PRD 11 offline/export: no completed encrypted authorized trip cache, last-sync/freshness policy, restart-safe offline journey, protected-cache controls, export preview/field selection or itinerary text/PDF/image/calendar export. Form drafts and SDK caching do not satisfy that scope.
  • Queued offline edits and offline maps are deferred. A reliable continuously live collaboration subscription is not established by the current get/list repository paths; test refresh/reopen behavior.
  • AI weather/compatibility enrichment is deferred. “Check details” is a review/disclosure action, not a live booking/opening-hours verification service.
  • Reminder delivery and AI-completion notifications: a Reminders preference exists, but the inspected push categories/sources do not implement reminder scheduling or AI job completion push.
  • Auth recovery and profile media: no password-reset or email-verification UI/SDK calls were found; avatar/photo upload is not implemented (initials are used).
  • Community refinements: destinations use a fixed 12-place catalog. Re-requesting after withdrawal/decline is rejected while the previous request document exists. Moderator work is via an operator CLI/callable, not a mobile moderation dashboard.
  • Full dark mode: the shared app explicitly uses a light color scheme. Accessibility/layout polish still needs the device matrix.

Implemented, but not release-verified

Community deployment/readiness/App Check; signed Google/Apple auth; FCM/APNs; production RevenueCat credentials/products and verified webhook convergence; signed Android/iOS purchase/restore/refund/expiry; HTTPS link associations; published legal/support pages; protected-data cleanup/retention on signed devices; store listings/public release and measured growth dashboards. None was completed merely by writing this guide.

Chat, expense splitting, travel booking/payment collection and background checks are not part of the shipped scope described here. Do not test them as existing features.

Prepare your test run

  1. Pick the environment and build. The checked-in Android JSON/iOS plist target live triptandem. Debug does not mean emulator or staging. Use disposable accounts/trips and keep production rollout changes under the release owner’s control.
  2. Use at least two installations. Prefer Android + iOS; add another session/device for a viewer or race tests. Use the same current app source/build pair. Confirm a saved trip appears from the second installation so an in-memory fallback cannot masquerade as a backend pass.
  3. Create test identities: A host/owner, B editor, C viewer, D applicant, E second applicant/race participant, and a separate moderator operator. Some cases can reuse signed-out sessions, but races need simultaneous sessions. Use recoverable emails you control; keep a Pro billing identity separate from Free limit tests.
  4. Prepare a reusable fixture: Kyoto, Japan; timezone Asia/Tokyo; start today +30 days, end +32; capacity 4; Planning; Private; Balanced; Moderate; JPY; English; Food/Culture. Keep the dates in the future every time you rerun.
  5. Run the baseline first. Leave every flag off, complete B01–B10 and C01–C08, then the Pro catalog/cancel checks. AI/community/push are later passes after prerequisites. Save destructive R04/R05 until fixtures are no longer needed.

A quick 30–45 minute smoke run

This is a planning estimate, excluding setup and purchases: B01 → B04 → B06 → C01 → C02 → C05 → P01 → C06. Restart both apps, confirm persistence, and finish with R04/R05 on disposable fixtures. A full regression needs separate AI, billing, community, push and failure/race runs.

  • Publishing AND discovery must both be true. Both the shared community surface and server gate require their conjunction. The Discover tab can still exist while gated, showing “Community trips are not open yet”. Trip → Community can also display the gate.
  • Join requests additionally need join_requests_enabled. New requests and approvals require all three. Existing request status/withdraw/decline and safety/history operations have different gates; do not assume all history disappears when acquisition switches off.
  • Pro is an entitlement, not a Remote Config flag. triptandem_pro and verified webhook state control limits. Manual planning, private invites, joining and safety are not paid feature flags.
  • Activity is independent of push. Its server function and App Check must work with push off. Private membership/trip-change events can exercise push without opening community discovery.
  • Set the reviewed default, not just a tester condition. AI/community/push server checks read template defaults. A client-only conditional true or changed XML default cannot authorize backend work.

Refresh and rollback procedure

  1. Record project, current template version and all five values. Have the release owner publish the approved test recipe after its prerequisites pass; changing a local file alone does not update Firebase.
  2. Cold-relaunch both clients with network available. Android fetches on activity creation; debug minimum interval is 0, release is 3,600 seconds. iOS also configures 0/debug and one hour/release. There is no dedicated in-app forced-refresh control.
  3. Allow up to the 10-second client fetch timeout. The AI server caches its gate for up to 30 seconds. Record actual fetched behavior rather than assuming an instant kill switch.
  4. Check false → true, then true → false, malformed/missing values and offline cold launch. A failed fetch publishes safe false defaults. New feature entry points/operations must reflect the gate; previously saved plans are retained.
  5. Restore the approved values after testing and recheck both clients and new backend operations. This document has not changed any live flag.

How an operator approves a held test listing

The repository provides scripts/moderate_community.mjs. It is hardcoded to the live triptandem endpoint; it is not a staging selector. The operator needs a Firebase ID token with the communityModerator=true custom claim plus a valid App Check token, stored in private credential files.

Create an action JSON file for queue inspection:

{ "operation": "queue" }

After reviewing the listing, use another action JSON file (replace TRIP_ID):

{
  "operation": "publish_reviewed",
  "subjectId": "TRIP_ID",
  "policyBasis": "Reviewed disposable QA listing against community guidelines"
}

From the repository root, with the two credential-file environment variables set by the operator:

node scripts/moderate_community.mjs /path/to/action.json

Required environment names: MODERATOR_ID_TOKEN_FILE and MODERATOR_APP_CHECK_TOKEN_FILE. Do not paste credential contents into command arguments, this guide or result notes. The normal app cannot self-assign moderator claims. A changed preview must be resubmitted; do not manually force the listing status to pass the test.
